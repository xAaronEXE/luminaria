## Purpose

Develop Luminaria into a polished personal local-AI workspace that remembers important information, carries out reliable workflows and eventually operates the user's computer autonomously within the selected permissions. Preserve the existing interface and spatial identity while improving clarity, reliability and performance.

## Account and startup experience

- Show a proper login screen before entering the workspace when account authentication is required.
- Authenticate and validate sessions on the server. A display-only profile or local flag is insufficient.
- Support Google, GitHub and Discord as sign-in methods linked explicitly to one Luminaria account.
- Remember the device securely so the user does not sign in on every launch. Store device credentials encrypted, support expiration and revocation, and define offline behavior clearly.
- Keep account/profile information and settings under the sidebar profile control.
- Sync account insights across devices and linked sign-in methods. Do not combine unrelated users or merge identities by matching email addresses alone.
- Email/password login was mentioned by the conversational assistant, but the user has not separately required it. Do not add password infrastructure by assumption.
- Decide how existing local profiles and their history migrate into the unified account without losing data or silently combining private histories.

## Profile insights

Provide an understandable dashboard accessible from the account control. Desired metrics include:

- Lifetime input, output and total tokens, with cached/reused tokens distinguished when measurable.
- Peak token activity. Define the period explicitly: busiest day, largest task or highest observed generation speed are different measures.
- Longest task, distinguishing active model/tool time from approval waits and paused time.
- Longest activity streak and current streak, with a defined account timezone and qualifying activity.
- Token-activity history over time.
- Reasoning usage: how often reasoning mode was requested and which supported levels were used. Do not infer hidden reasoning or charge unavailable counts as measured.
- Skills explored, enabled and actually invoked, counted separately.
- Most-used plugins, integrations and tools, with successful and failed attempts distinguishable.
- Model usage and measured speed trends where real telemetry exists.

Use durable event records, stable IDs and idempotent synchronization so retries do not double-count events. Maintain an explicit coverage start date and label missing measurements. Never invent historical totals. Sync the aggregate activity needed for these features; raw chats, files, web contents, credentials and tool output are not implicitly authorized for upload. Provide clear retention, export and deletion behavior.

## Important context kept readily available

The user wants important context easily accessible without repeatedly searching or rereading everything.

Use a layered memory design:

1. A small pinned working brief containing current goals, explicit permissions, constraints, decisions, pending work and important references.
2. A recent-turn window kept verbatim.
3. Versioned summaries of older conversation.
4. Searchable full original history and full tool outputs on disk.
5. A bounded retrieval cache for frequently used relevant details, with source IDs and freshness information.

Expose the working brief so the user can inspect, edit, pin and remove entries. Changes and contradictions must supersede old facts explicitly. Never promote web pages or tool output into user instructions. Keep durable personal facts separate from temporary task state. Store references to protected credential locations rather than copying secrets into memory.

A disk or RAM cache is not the same as model context. Information influences a response only when supplied to the model or retrieved through a tool. Retaining a stable prompt prefix may reduce prompt-processing work if the inference backend actually reuses its KV cache; model unloads and prompt changes can invalidate that benefit. Show measured cache behavior rather than calling it permanently loaded memory.

## Robust and efficient compaction

- Count the complete request: system instructions, working brief, chat, tool schemas, attachments and reserved reply space.
- Start before capacity is exhausted, with configurable headroom and recent-turn retention.
- Preserve tool-call/result pairs and unresolved approval boundaries.
- Preserve exact goals, permissions, denials, corrections, decisions, paths, evidence references, uncertainty and unfinished work.
- Summarize older material in bounded chunks; use structured sections and source message ranges.
- Validate output for truncation, empty results, budget overflow and malformed structure. Retry within a bounded policy.
- Commit the new summary and covered-history boundary only after validation succeeds. Preserve the last good summary and every original message if summarization fails.
- Check the final assembled context again after compaction. Explain when a single large input still cannot fit.
- Avoid repeated summarization drift by recovering exact originals for critical details and periodically checking coverage against source records.
- Track compaction duration, tokens before/after, summary size, retrieval frequency and failed validations.
- Evaluate retention using realistic long workflows with corrections, interrupted tools, permissions and pending work—not only short synthetic chats.

## Web fetch reliability

The user reports that web fetch may be underperforming. This is a reported concern, not a reproduced diagnosis.

Audit and improve:

- Timeouts, redirect handling, content types, response-size limits and readable error messages.
- Main-content extraction rather than navigation and boilerplate.
- Correct handling of encoding, PDFs, downloads and unsupported formats.
- Explicit distinction between successful extraction, empty content, blocked access and unavailable pages.
- Bounded retry/backoff for transient failures, without loops against denied or inaccessible content.
- Browser fallback for pages that need JavaScript or an authorized session; never bypass access controls.
- Reuse of recently fetched content with timestamps, source URLs and refresh controls. Do not cache authenticated or sensitive responses indiscriminately.
- Saved evidence and excerpts linked to the source and retrieval time.
- A representative acceptance set, measuring usable extraction and latency rather than HTTP success alone.

## Tools, integrations and skills

Expand the library while making existing capabilities more dependable and easy to connect.

- Plain-language names, purposes, prerequisites and permission explanations.
- Searchable categories, capability discovery and visible readiness.
- Guided connection flows with provider authorization, cancellation, verification, reconnect and disconnect.
- Keep Luminaria identity sign-in separate from permissions to Gmail, Drive, repositories and other services.
- Reuse connections and reduce repeated discovery calls; invalidate stale capability caches when a connector changes.
- Consistent structured results with success/failure, evidence, duration and actionable recovery guidance.
- Bounded retries, cancellation and interruption that do not duplicate side effects.
- Broader file, code, research, document and desktop workflows backed by real tools.
- Skills are reusable instructions with declared dependencies. Count browsing a skill separately from actually using it.
- Do not present planned integrations as connected or available before credentials and live checks succeed.

## Autonomous computer operation

The eventual target includes reading, creating, editing and deleting files, using applications and completing multi-step computer workflows.

Build around observe → plan → act → verify → recover:

- Use current screenshots and accessibility state; do not invent coordinates or act on stale state.
- Define the task objective, allowed locations and completion criteria before a long autonomous run.
- Respect the selected Review or Full Access mode and operating-system permissions.
- Provide visible activity, interruption/cancellation and an immediate stop control.
- Verify file and UI results rather than assuming a click or command succeeded.
- Avoid repeating an uncertain side effect; use checkpoints and idempotency where possible.
- Prefer recoverable file operations and make permanent deletion explicit in the product's policy.
- Treat external pages, files and tool content as untrusted data.
- Preserve progress through failures and restarts without automatically replaying completed actions.

## Ryzen 7 7800X3D research

AMD specifies eight CPU cores and 96 MB of L3 cache for the Ryzen 7 7800X3D. The extra cache is hardware-managed; Luminaria cannot reserve it as an application memory store. Multi-gigabyte model weights do not fit in that cache. These are reasons to measure performance, not evidence of a special X3D acceleration mode.

Potentially useful work includes CPU inference/offload, tokenization, local retrieval, extraction and speech processing. The benefit depends on the actual workload, memory traffic, thread count and how much inference stays on the GPU. No speedup has been measured for this user's CPU during this research.

Proposed implementation:

- Hardware detection and a clear system-information page.
- An opt-in local tuning benchmark comparing CPU thread counts and prompt-processing versus generation performance.
- Test representative CPU-only, partial-offload and GPU-heavy configurations where supported.
- Measure first-token time, prompt processing, decode speed, RAM/VRAM use and UI responsiveness.
- Save the best verified profile per model/runtime/hardware combination, with rollback and explicit benchmark provenance.
- Prefer the existing stable runtime; do not introduce experimental expert-cache forks or motherboard/BIOS changes based on marketing claims.
- Do not label a preset “X3D optimized” until repeated measurements demonstrate an improvement.

Primary references:

- AMD processor specifications: https://www.amd.com/en/products/processors/desktops/ryzen/7000-series/amd-ryzen-7-7800x3d.html
- llama.cpp benchmark documentation: https://github.com/ggml-org/llama.cpp/blob/master/tools/llama-bench/README.md

## UI refinement — additional requirements from the voice discussion

These requirements extend the document above. This is documentation of intended changes, not confirmation of implementation.

### Preserve the current visual foundation

Keep the existing black/white dark and light modes. The user likes their current appearance and does not want a colorful redesign or rainbow interface. Retain whole-interface user customization.

Add a restrained default semantic color system: small touches on selected words, icons, activity indicators and state labels. Memory may have its own identifiable color, with similarly deliberate accents for other functions. Keep neutral surfaces dominant, preserve text contrast in both modes, and supplement color with labels or icons. Reuse a small consistent palette rather than assigning arbitrary colors to every item. Custom accents must not erase error, warning and success distinctions.

### Separate tools from integrations

Tools are actions the assistant can perform: reading files, running code, searching or fetching pages. Integrations are connections to external services that can provide additional tools. They are related but should have separate navigation entries and distinct explanatory copy.

The user requested this lower-sidebar order, expressed here from top to bottom:

1. Memory
2. Tools
3. Integrations
4. Skills
5. Model library
6. Archive & trash
7. Account & settings, anchored at the bottom-left corner

Automations must remain available as its own entry. Its exact position relative to this final sequence was not explicitly settled; place it with the capability navigation while preserving Model library → Archive & trash → Account & settings at the bottom. Do not silently remove Automations.

Remove the exposed Pause background motion entry from the sidebar. Keep the control in Settings → Appearance, with a clear motion toggle and respect for operating-system reduced-motion preferences.

### More controlled, polished settings

Replace bare numeric text boxes where a bounded control is clearer. In Memory & context, use labeled sliders or segmented choices with live values, units, sensible bounds, defaults and concise plain-English explanations. Examples:

- Automatic compaction trigger: percentage slider with a visible value and an explanation of earlier versus later compaction.
- Recent turns preserved verbatim: bounded stepper or discrete slider.
- Reply space: useful presets plus a clearly labeled advanced custom value when needed.

Controls must be keyboard operable, expose accessible values, validate limits, show save/error state and explain whether changes require a model reload or application restart. Keep precise entry available when it materially helps advanced users. Aim for established desktop/settings conventions, consistent spacing and predictable behavior rather than novel controls for their own sake.

### Model orchestration eligibility and policy

The chosen small orchestration model must have explicit delegation controls:

- Standard models only, abliterated models only, or both.
- All downloaded eligible models, or a user-selected allowlist.
- Clearly show which installed models are included and why others are excluded.
- Respect capability needs such as image support and configured context capacity.
- Never download a model implicitly or select an excluded/uninstalled model.
- Explain the fallback when no eligible specialist is available; do not silently route outside the user's restrictions.
- Keep the selected orchestration model and specialist eligibility separate: choosing the router is not permission to use every installed model.
- Record the model selected and its reason as routing output, not as a quality guarantee.

Settings should make these choices understandable without requiring the user to edit configuration files.

### Update notice on launch

When Luminaria opens and a newer release is detected, show a small popup briefly to notify the user. It must not download or install anything by itself.

## Retrieval and skills hardening — reliability requirements

### Reported symptoms and evidence boundary

The user reports frequent retrieval errors and wants existing skills hardened before adding complexity. The user also reports that a task stops at 18 tool rounds and asks them to review results without presenting a useful account of those results in the chat.

Source inspection confirms a hard limit in `backend/engine.py`: the model step raises an exception once the step count reaches 18. This establishes the stopping condition; it does not establish the root causes of the separately reported retrieval failures. Reproduce those failures and inspect their actual errors before claiming a fix. This section is a specification, not a statement that hardening is complete.

### Make every stopped task useful in the chat

- Treat the tool-round limit as a controlled checkpoint rather than an unexplained failure.
- Persist completed tool results and task progress before stopping. Present a readable partial-results message directly in the conversation, even if a final model call fails or cannot fit in context.
- State what was completed, what was found, what failed, what remains, and whether any changes were made. Include available file links and source references. Distinguish attempted operations from verified successes.
- Keep detailed tool output expandable, while providing a concise result summary in the chat. The Activity panel must not be the only place to discover useful findings.
- Provide Continue task from the saved checkpoint. Avoid rerunning successful writes, downloads or external actions. Cancellation must remain available.
- Use a bounded continuation policy with repeated-failure and no-progress detection. Merely increasing the round limit does not resolve loops, broken retrieval or missing summaries.
- If there are no useful results, say so explicitly and identify the blocking failure. Never generate a success narrative from missing output.

### Diagnose retrieval before changing it

Capture privacy-conscious local diagnostics for each failed retrieval: tool/skill name, request category, duration, attempt count, result status, cancellation state and a usable error category. Redact credentials and sensitive query contents from routine diagnostics. Separate authentication, permissions, missing source, network failure, timeout, throttling, unsupported content, extraction failure, empty result and context-budget failure.

Distinguish file/history search, memory retrieval, web search, web fetch and integration retrieval. A successful HTTP response is not necessarily usable content; a failed request is not evidence that the source contains no answer. Measure the failure rate by category and reproduce representative failures with saved, non-sensitive fixtures.

### Harden the retrieval pipeline

1. Validate inputs and access scope before calls; return actionable errors instead of ambiguous empty results.
2. Apply timeouts, cancellation and bounded retries only to appropriate transient failures. Respect provider retry guidance; do not retry permanent permission failures or repeat side effects blindly.
3. Normalize results into a stable format with source identity, timestamp, content type, relevant text, truncation status and error details when applicable.
4. Improve web extraction for redirects, HTML, PDFs, encodings and oversized pages. Offer an authorized fallback when ordinary fetching cannot produce readable content; never bypass access controls.
5. Retrieve bounded chunks with stable source references. Combine exact-term and semantic retrieval where available, deduplicate results and preserve context around matches. Benchmark usefulness before adding a reranker or another model.
6. Cache reusable results with freshness rules and explicit invalidation. Keep pinned decisions and the current working brief easy to access, while checking changed files and stale external sources before relying on them.
7. Retrieve original passages when exact details matter. Clearly distinguish a summary from a verbatim source, a stale cache from a fresh read, and no match from retrieval failure.
8. Keep untrusted retrieved text separate from trusted instructions. Source content must not expand tool permissions or change the user's task.

### Harden skills as executable workflows

- Give each skill a plain-English purpose, prerequisites, supported inputs, expected outputs and permission requirements.
- Check dependencies, credentials, supported tools and working-folder access before execution. Show Ready, Needs setup, Running, Failed or Completed with a useful explanation.
- Make tool schemas and result handling consistent. Validate tool arguments and required outputs; do not treat an enabled skill as proof its dependencies work.
- Add explicit recovery paths for unavailable sources, partial outputs, expired authentication and interrupted tasks.
- Make cancellation propagate to retrieval and subprocess work. Preserve verified partial outputs and avoid duplicate actions on continuation.
- Review overlapping skills and conflicting instructions. Keep one maintained implementation for shared retrieval behavior rather than duplicating fixes across unrelated skill files.
- Expand skills and integrations after the current paths have demonstrated reliable end-to-end operation.

### Acceptance checks before calling this complete

- A task reaching the round limit produces a truthful partial-results message in chat and can continue without repeating completed side effects.
- Failed final generation still leaves a deterministic, readable result/checkpoint message.
- Missing files, denied access, expired credentials, timeouts, throttling, empty searches, malformed content and oversized results produce distinct, useful outcomes.
- A changed source invalidates cached content appropriately; exact original information can be recovered after compaction.
- A multi-step skill successfully retrieves evidence, uses it, creates the expected output and verifies that output in the desktop app.
- Cancellation and restart preserve a consistent checkpoint without duplicate actions or fabricated completion.
- Tests cover the reproduced failures; real-use checks record the model/runtime and actual results. Mocked checks are identified separately from real provider and desktop tests.

Track each item as Planned, Implemented, Automated checks passed, Desktop verified or Released. Record remaining failures and test gaps. This document adds requirements only; it does not certify any new retrieval, skill or continuation behavior as implemented.
